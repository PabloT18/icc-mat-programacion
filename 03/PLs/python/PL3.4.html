PL3.4 · Procesamiento reproducible de archivos

Objetivos prácticos

  • Integrar archivos, funciones, registros y módulos.
  • Entregar una ejecución reproducible con diagnóstico de errores.

Contexto

Crear una herramienta que lea registros codigo;cantidad desde UTF-8, valide cada línea y genere un reporte en otro archivo. Separar lectura, procesamiento y entrada del programa.

Recursos y tiempo

Computador, Python, editor, terminal y Git. Utilizar bibliotecas estándar. Tiempo estimado docente: 6 horas. Esta estimación no modifica las horas oficiales del programa.

Instrucciones y restricciones

  • Crear main.py, lectura.py y analisis.py.
  • Aceptar códigos no vacíos y cantidades enteras no negativas. No permitir ; dentro del código.
  • Ignorar líneas vacías y registrar número de línea para rechazos.
  • Conservar duplicados y orden de registros válidos.
  • Generar cantidad de registros, suma de cantidades y promedio con dos decimales.
  • No sobrescribir el archivo de entrada y no producir interacción al importar utilidades.

Actividades por fases

1. Contratos y datos

Definir formato y preparar archivos normales, vacíos e inválidos.

Registrar un commit funcional: feat(pl3.4): fase-1-descripcion. Sustituir descripción por el cambio realizado y conservar el hash real.

2. Lectura

Gestionar ruta inexistente, UTF-8 y errores de registros con número de línea.

Registrar un commit funcional: feat(pl3.4): fase-2-descripcion. Sustituir descripción por el cambio realizado y conservar el hash real.

3. Procesamiento y reporte

Retornar datos desde utilidades y escribir el informe desde la capa de entrada.

Registrar un commit funcional: feat(pl3.4): fase-3-descripcion. Sustituir descripción por el cambio realizado y conservar el hash real.

4. Reproducción

Ejecutar desde una copia limpia, registrar versión real y comparar archivos esperados.

Registrar un commit funcional: feat(pl3.4): fase-4-descripcion. Sustituir descripción por el cambio realizado y conservar el hash real.

Resultados que registrar

Construir una tabla con caso, entrada, resultado esperado, resultado real y evidencia. Anotar el comando, la versión y el hash del commit entregado. Registrar limitaciones y pruebas que no se hayan completado.

Defensa

  • Explicar diferencia entre error de archivo y error de dato.
  • Repetir una prueba desde otra carpeta.
  • Cambiar un contrato y localizar los módulos afectados.

Explicar el código del commit entregado, ejecutar una prueba nueva y realizar una modificación pequeña. Declarar herramientas utilizadas y comprobar personalmente sus resultados.

Conclusiones

Redactar tres conclusiones relacionadas con casos realmente ejecutados: corrección de la regla, decisión de diseño y límite observado.

Recomendaciones

Proponer una mejora concreta, justificarla con una prueba y explicar qué partes de la solución cambiarían.
